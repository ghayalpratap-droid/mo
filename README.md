# People — Employee Management System

Spring Boot 3.5 / Java 17, PostgreSQL 17, React 19, Vite and Axios. The directory supports create, list, individual details, search, edit and confirmed deletion. Names and address are required; names accept Unicode letters, spaces, apostrophes and hyphens, and reject digits and other symbols; age must be a whole number from 18 to 100. IDs are generated by PostgreSQL.

## Laptop development with H2 (no PostgreSQL or Docker required)

Install Java 17+ (JDK), Maven 3.9+ and Node 22.12+. Open two terminals in VS Code at the repository root.

Backend terminal:

```sh
cd backend
mvn spring-boot:run -Dspring-boot.run.profiles=local
```

Frontend terminal:

```sh
cd frontend
npm ci
npm run dev
```

Open http://localhost:5173. The local profile uses a persistent H2 database at `backend/data/employees` and binds the backend to the laptop loopback interface. PostgreSQL credentials are unnecessary for this profile. Stop each terminal with Ctrl+C. Records persist across restarts; deleting `backend/data` deletes your local records. If port 5173 is occupied, stop the other Vite instance before starting this project.

Optional H2 console: http://localhost:8080/h2-console. JDBC URL: `jdbc:h2:file:./data/employees`, username `sa`, empty password. This console is for local development only. The default profile and Docker deployment continue to use PostgreSQL.

## Local development with Docker

```sh
cp .env.example .env
# Set POSTGRES_PASSWORD to a strong local password in .env.
docker compose up --build -d
# Frontend: http://localhost:3000
# Backend: http://localhost:8080/api/employees
curl --fail http://localhost:8080/actuator/health
python3 scripts/smoke.py
docker compose down
```

The named PostgreSQL volume retains records across restarts. `docker compose down -v` permanently removes local data. The smoke test creates Rahul Sharma, reads and updates the record, tests invalid requests and removes only its own record.

For hot reload, run `docker compose up -d db`, export DATABASE_URL (`jdbc:postgresql://localhost:5432/employees`), DATABASE_USERNAME (`employees`), and DATABASE_PASSWORD (matching your local password), then run `mvn -f backend/pom.xml spring-boot:run`. In another terminal: `cd frontend && npm ci && npm run dev`. Vite proxies `/api` to port 8080.

## Checks

Java 17+ and Maven 3.9+: `mvn -f backend/pom.xml verify`. Unit tests cover service behavior; MockMvc integration tests exercise CRUD, validation, missing records, CORS and health using isolated H2. The PostgreSQL smoke test validates the real database workflow separately.

Node 22.12+: `cd frontend && npm ci && npm test && npm run build`. Frontend tests cover validation, form submission, listing/search, editing, delete confirmation and API failure/retry.

## Production deployment

Deployment has not been provisioned by these files alone. Review pricing before applying `render.yaml`: its persistent database and web service use paid plans. A free trial database is unsuitable for permanent employee storage.

1. In Render, connect this repository and create the PostgreSQL database and Docker web service from the reviewed blueprint. Use backend root directory `backend` and `/actuator/health` as the health path. Set DATABASE_URL to the **JDBC** URL `jdbc:postgresql://HOST:5432/DATABASE` (with `?sslmode=require` if required), DATABASE_USERNAME and DATABASE_PASSWORD from the managed database. Render's `postgresql://` connection string is not a JDBC URL. Set CORS_ORIGINS to the exact Vercel production origin. PORT is supplied by Render.
2. In Vercel, import the same repository, set root directory `frontend`, Vite framework, `npm run build`, and output directory `dist`. Set VITE_API_BASE_URL to `https://YOUR-BACKEND/api` before building. Update Render CORS_ORIGINS after receiving the frontend origin.
3. Configure GitHub production environment secrets RENDER_DEPLOY_HOOK and VERCEL_DEPLOY_HOOK and variables BACKEND_URL / FRONTEND_URL. Configure production environment approval protection if desired. Disable independent automatic deployment in both providers so CI controls deployment. The main workflow runs tests before calling hooks and checks public health and frontend HTML afterward. Those checks do not prove that the newest revision is deployed; verify the provider deployment revision and run the CRUD scenario on the live site.
4. Run `BACKEND_URL=https://YOUR-BACKEND python3 scripts/smoke.py`. Open the production site, create Rahul Sharma (28, Pune, Maharashtra), refresh, verify persistence, edit age to 29, then delete and verify removal. Verify the browser has no CORS failures.

API: POST/GET `/api/employees`; GET/PUT/DELETE `/api/employees/{id}`. Errors return a message and, for validation errors, field errors. Database failures return 503 without disclosing credentials.

**Access control:** this specification includes no authentication. CRUD endpoints are open to anyone who can reach them. Use only demo data in a public deployment; add authentication/authorization before storing real employee information. Hibernate schema update is convenient for this initial version; use versioned migrations before evolving a production database.

## Prepared cloud workspace

The onboarding environment supplies Docker, Node and Python. `bash scripts/cloud-install.sh` prepares a verified Java 17/Maven toolchain in `/workspace/tools`, installs the frozen frontend lockfile, and runs backend/frontend tests and builds. It uses the platform proxy and system trust store without disabling TLS checks. `bash scripts/cloud-start.sh` starts Compose PostgreSQL plus the backend and Vite frontend, generates an ignored local database password if needed, and runs the PostgreSQL API smoke test. Repeat the startup command after restoring a cloud snapshot; processes do not survive publication.

Optional browser check: install Python Playwright and its Chromium browser, then run `python3 scripts/e2e.py`. In this prepared cloud machine use `CHROMIUM_PATH=/usr/bin/chromium python3 scripts/e2e.py`. The script tests CRUD, page refresh, validation and mobile layout; it assumes an otherwise empty demo directory. Do not run it against real employee data. Screenshots go to `/tmp/employee-desktop.png` and `/tmp/employee-mobile.png`.

## Interaction and activity history

The header includes History, About and Instagram/Google/YouTube links. Social links open the public service homepages in a new tab; the animated banner is decorative and has no advertising integration. Button clicks use a short Web Audio tone, with a header mute toggle saved locally. Saved employees bounce and scroll into view. Reduced-motion preferences disable animations.

`GET /api/history` returns the latest 200 activity entries, newest first. Employee creation, updates and deletion write a history entry in the same database transaction, including a name/ID snapshot and UTC timestamp. The frontend displays timestamps in the browser's local timezone. History remains after employee deletion and database restarts; older entries remain stored but are not shown by this endpoint. Existing employee records gain history only when changed after this feature is installed. The H2 local profile creates the activity table automatically without deleting existing employees.
